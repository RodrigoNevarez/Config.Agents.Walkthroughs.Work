#+TITLE: Flashcards Guide
#+DATE: 2026-08-24

Single source of truth for =.agents/flashcards/= — a personal
spaced-repetition study feature, one deck per topic, mined from an archived
walkthrough's own =.agents/walkthroughs/archive/<uuid>.org=. Referenced by
[[file:00-conventions.org][00-conventions.org]] instead of restating its
shared UUID and cross-reference rules, same principle as
[[file:05-wiki-guide.org][05-wiki-guide.org]] uses for =.agents/wikis/= — a
full top-level sibling of =.agents/walkthroughs/=, documented from inside
this directory rather than its own.

* Purpose

A walkthrough package and a wiki page are both built to be *read* — worked
through once, or scanned for current state. Neither is built to be
*remembered*. This feature exists to close that gap: it mines the reasoning
already captured in an archived walkthrough and turns it into atomic recall
prompts, reviewed on a real spaced-repetition schedule, so the *why* behind a
settled decision stays retrievable months after the walkthrough that taught
it was last opened.

This is deliberately narrower in scope than it could be. Two things it is
*not*:
- *Not a second copy of the walkthrough.* A card tests one atomic fact or
  mechanism and links back to its source rather than restating the
  walkthrough's own reasoning — see Deck Template, below.
- *Not a scheduling engine.* Reinventing SM-2/FSRS in this repo would be
  wasted effort against a correctly-implemented, well-benchmarked scheduler
  that already exists. This feature authors *content* in git; actual review
  and interval scheduling happen in a real spaced-repetition application
  (Anki) outside the repo. See Export Workflow and Anki Setup, below.

*Scope, for now: archived walkthroughs only.* =.agents/wikis/= pages hold a
different shape of content (current-state facts, not reasoning history) and
are deliberately out of scope for a first version of this feature — a
natural second wave once this one is proven out, not a gap in the design.

* Directory Structure

#+begin_src text
.agents/flashcards/
  index.org               - entry point: one line per mined deck, plus
                             which archived walkthroughs have none yet
  <uuid>/                  - one directory per mined walkthrough, named with
                              that walkthrough's own :ID: (same uuid as its
                              .agents/walkthroughs/archive/<uuid>.org — no
                              new uuid gets generated for the deck itself)
    deck.org                - the deck's cards, source-of-truth content
    anki-export.txt          - this deck's own Anki-importable export
                                (build artifact, see Export Workflow)
  SCRIPTS/
    export-anki.py           - <uuid>/deck.org -> that same directory's
                                anki-export.txt
    validate-flashcards.py   - mechanical checks, see below
    find-card.py              - looks up one card by id/prefix across every
                                 deck, for a live Study Session (see below)
                                 to grade an answer against
#+end_src

A deck directory's name is the walkthrough's own uuid, reused deliberately —
see UUID Placement, below — but the two live in genuinely separate
directories (=.agents/flashcards/<uuid>/= vs.
=.agents/walkthroughs/archive/<uuid>.org=), the same top-level relationship
=.agents/wikis/= already has to =.agents/walkthroughs/=.

Each deck keeps its own export artifact next to its own source, rather than
one combined file for the whole feature — reviewing, re-exporting, or
re-importing one deck never touches any other deck's output.

There is no =CHANGELOG.org= here, unlike =.agents/wikis/=. A wiki page
mutates in place to track the project's *current* truth, so a changelog is
what lets a reader recover its history. A deck only grows — cards get added
as more of the archive gets mined, but a card, once written, is never revised
to reflect a new decision (its source walkthrough is already immutable).
Git's own history is a complete record of that growth; a second,
hand-maintained log would just duplicate it.

** UUID Placement

Same rule as the rest of this system: every card gets a permanent =:ID:= via
a =:PROPERTIES:= drawer. See
[[file:00-conventions.org][00-conventions.org]]'s UUID Convention section —
generate with a real generator, never hand-type one, and it must be unique
across the entire shared namespace that convention covers
(=.agents/walkthroughs/=, =.agents/wikis/=, and =.agents/flashcards/=).

*CRITICAL RULE — a deck directory's own name is not a fresh UUID.* It is the
*same* =:ID:= as the archived walkthrough it was mined from, reused
deliberately. This makes a deck's source unambiguous from its directory name
alone, before ever opening it.

* Deck Template

=deck.org= carries a fixed =* For AI Assistants= section — identical
boilerplate across every deck, the same "fixed, identical text" discipline
=02-expansion-guide.org= already applies to =walkthrough.org='s own section
of the same name — followed by one =* Card: <heading>= section per card, a
real atomic recall prompt, never a summary of an entire step. Two card types
are allowed, chosen per card based on what's actually being tested (see
Authoring Workflow's format CRITICAL RULE, below):

#+begin_src org
#+TITLE: Flashcards — <Walkthrough Title>
#+DATE: <ISO date>

Source walkthrough: [[file:../../walkthroughs/archive/<uuid>.org][<Walkthrough Title>]]

* For AI Assistants

If you are an AI assistant (any provider) reading this file — dragged into a
plain chat window, pasted directly, or loaded some other way — read this
before doing anything else.

- *What this file is.* Each =* Card: ...= section below is one atomic
  spaced-repetition flashcard, mined from a real, already-settled engineering
  decision (its =*Source:*= link names exactly which one). This is not
  material to freely improvise on or correct — if something here looks
  wrong, say so to the human rather than silently "fixing" your quizzing to
  match what you think is right instead.
- *Your job is to quiz, not to lecture.* Present cards one at a time, in
  order (unless the human asks to jump around), and let the human attempt a
  real answer from memory before you reveal anything. This file exists for
  active-recall practice — reading it straight through at them defeats the
  entire point.
- *CRITICAL — for a Cloze card (=:TYPE: cloze=), never reveal the
  =\{\{c1::...\}\}= content when presenting the front.* The literal answer is
  sitting in the file's own heading text (e.g. =\{\{c1::Tools\}\}=) — when
  you show the human this card, replace that span with a blank (e.g.
  "_____") and only reveal the real text once they've attempted an answer.
  Pasting the card's heading verbatim spoils it instantly.
- *Grade against the card's own =*Back:*= (or the un-blanked cloze text) —*
  don't paraphrase from your own general knowledge of the topic, even if you
  think you know it better. If the human's answer is right but thin, tell
  them what they left out. If they're stuck, ground your hint in the card's
  own =*Source:*= citation, not an abstract restatement of the question —
  give one grounded hint, one retry, then just explain it and move to the
  next card.
- *Anki isn't right/wrong — it grades on four buttons, and your job is to
  help the human pick one, not just say "correct."* You don't click
  anything yourself; the human does, in Anki, after this conversation. Map
  what actually happened onto:
  - *Again* — wrong, or only got there with your hint/retry. Anki re-shows
    it within a minute.
  - *Hard* — right, but it took real struggle: hesitation, a guess, or
    fumbling toward the answer before landing on it, even with no hint from
    you.
  - *Good* — right, with a normal, clean attempt and nothing notable about
    how it went. This is the default correct rating — reach for it first.
  - *Easy* — right, instantly, with total confidence. Use rarely; most
    correct answers are Good, not Easy.
  *CRITICAL — you cannot observe hesitation or response time the way Anki
  can.* Base your suggestion only on what's actually in the conversation —
  did they need a hint, hedge ("I think...", "maybe...?"), or self-correct
  — and if it's genuinely unclear whether a clean-but-uncertain answer was
  Good or Hard, ask the human directly rather than guessing confidently at
  something you can't see.
- *This is supplementary practice, not the real spaced-repetition review.*
  The actual schedule for these cards lives in the human's own Anki
  collection, driven by whatever they've imported from this deck's
  =anki-export.txt= — nothing in this conversation updates that. Don't tell
  the human a card is "done" or that they won't need to see it again; that
  call belongs to Anki's own scheduler once they mark it there, using
  whichever of the four buttons they end up actually picking — your
  suggestion is input to that, not a substitute for it.
- *At the end of the session*, list each card ID (the =:ID:= in each card's
  =:PROPERTIES:= drawer) you'd suggest as Again or Hard, plus any you were
  genuinely unsure about — that's what the human should double-check against
  their own felt sense before rating it in Anki, not the clean Goods.

* Card: <a real question testing the mechanism, not its exact wording>
  :PROPERTIES:
  :ID:       <uuid>
  :TYPE:     basic
  :END:
  *Back:* <the explanation a correct answer must cover>
  *Source:* [[file:../../walkthroughs/archive/<uuid>.org][<Walkthrough Title>]], step "<Step Title>"
  *Tags:* :<Domain>::<Subcategory>::<topic-slug>:

* Card: <a sentence with {{c1::the one atomic fact}} deleted>
  :PROPERTIES:
  :ID:       <uuid>
  :TYPE:     cloze
  :END:
  *Source:* [[file:../../walkthroughs/archive/<uuid>.org][<Walkthrough Title>]]
  *Tags:* :<Domain>::<Subcategory>::<topic-slug>:
#+end_src

A card's own deck lives at =.agents/flashcards/<uuid>/deck.org=; its source
walkthrough is =.agents/walkthroughs/archive/<uuid>.org= — two directory
levels up out of the deck (past =<uuid>/= and =flashcards/=), then across
into =walkthroughs/archive/=, hence =../../walkthroughs/archive/<uuid>.org=.

*Why this section earns its portability claim.* =For AI Assistants= is what
makes dragging just this one file into a completely different AI product
(Gemini, ChatGPT, any provider) actually work — see
[[file:02-expansion-guide.org][02-expansion-guide.org]]'s External Session
Workflow for the same rationale applied to =walkthrough.org=. Without it, an
AI reading a raw =deck.org= has no way to know cloze answers must stay
hidden, that grading should ground itself in =*Source:*=, or that nothing it
does here touches Anki's own schedule — all of that would otherwise only
live in this guide, which an external chat has no access to.

*CRITICAL RULE — every card needs a real =*Source:*= link.* It must resolve
to the deck's own source walkthrough,
=.agents/walkthroughs/archive/<uuid>.org=, and, for a step-specific fact,
name the actual step title inside that file — not a paraphrase from memory
of what the walkthrough said. Same evidentiary standard as everything else in
this system: verify the source is actually in there before citing it (see
=02-expansion-guide.org='s own CRITICAL RULE on this exact failure mode — a
citation that was never independently re-checked).

*CRITICAL RULE — a card tests the mechanism, not the walkthrough's exact
sentence.* Lifting a =*Why:*= line verbatim into a card's front produces cue
dependency: recognizing the sentence's shape instead of understanding what it
describes. Reword it — ideally against a slightly different framing of the
same mechanism than the walkthrough itself used. Same principle as
=03-quiz-guide.org='s own "test the mechanism, not the memory" rule; this
feature just applies it at a finer grain, per fact instead of per package.

* Tagging Scheme

Reuse [[file:../index.org][index.org]]'s own Domain and Subcategory headings
verbatim as a card's tag, plus a short kebab-case topic slug:
=:<Domain>::<Subcategory>::<topic-slug>:=. No new taxonomy gets invented here
— the index already organizes every topic this feature draws from, and
reusing it directly is what makes a whole domain bulk
suspendable/unsuspendable in Anki later, a hierarchical-tag pattern (=::= as
the nesting separator) Anki itself supports natively.

* Authoring Workflow

1. Pick an archived walkthrough not yet listed in
   [[file:../../flashcards/index.org][.agents/flashcards/index.org]] (or add
   to an existing deck, if revisiting one).
2. Read the whole walkthrough — Problem, every step's =*Why:*= and
   =*Result:*=, and Notes — not just its Quiz. The Quiz's 5 questions are
   useful cross-checks for what actually mattered, but they were authored for
   one live, open-ended grading session (per =03-quiz-guide.org=), not for
   atomic recall; a walkthrough's real content is finer-grained than 5
   questions.
3. For each mechanism or fact worth remembering independently, write one
   card. *CRITICAL RULE — pick the format deliberately, per card, not
   uniformly per deck.* Use Basic when the answer is an explanation of a
   mechanism (most of this feature's source material, since walkthroughs are
   mostly *why*-reasoning, not vocabulary). Reserve Cloze for a genuinely
   atomic fact — an exact threshold, filename pattern, flag, or rule name —
   where the "answer" really is a short, precise string. Defaulting
   everything to Cloze for authoring convenience risks cue dependency on
   reasoning-heavy content: a clozed sentence can be answered by recognizing
   its shape (length, phrasing, position of the blank) instead of actually
   reconstructing the mechanism, which defeats what this feature exists for
   (see Deck Template's own CRITICAL RULE on this).
4. Create or append to =.agents/flashcards/<walkthrough-uuid>/deck.org=
   (creating the directory the first time a given walkthrough gets mined). A
   brand-new deck starts from the Deck Template above, boilerplate =* For AI
   Assistants= section included verbatim — never skip it to save time; it's
   what makes the finished file worth dragging into another AI chat at all.
5. Add or update the deck's line in
   [[file:../../flashcards/index.org][.agents/flashcards/index.org]].
6. Re-run =SCRIPTS/export-anki.py= for this deck and the validator.

* Export Workflow

=SCRIPTS/export-anki.py= reads every =.agents/flashcards/<uuid>/deck.org=
and writes that same directory's own =anki-export.txt= — one export artifact
per deck, sitting next to the source it was generated from, not one combined
file for the whole feature. Per Anki's own text-import format
(=#key:value= header directives at the top of the file):
- One row per card: GUID, note type, field 1, field 2, tags.
- =#guid column:1= — the card's own =:ID:= is reused as the import GUID, so
  re-running the export after mining more of that deck *updates* existing
  notes instead of duplicating them; Anki's text-import format guarantees
  this specifically when a row's GUID already exists in the collection.
- =#notetype column:2= — =TYPE: basic= maps to Anki's built-in *Basic* note
  type (field 1 = Front, field 2 = Back); =TYPE: cloze= maps to *Cloze*
  (field 1 = Text, containing the =\{\{c1::...\}\}= span). Both note types
  can be mixed in one import file this way — no custom Anki note type needs
  to be created.
- =#tags column:5= — the card's own =*Tags:*= line.

The GUID column is an internal Anki field, not something a reviewer can read
off the card mid-session — so field 1 also gets the card's own =:ID:=
prefixed onto its visible text, muted and small (=[<first 8 hex chars>]=),
purely so a Study Session (below) has something short and legible to read
off the card's *front*, before it's flipped. This is presentational only —
authoring and citation always use the full UUID; only the exported,
Anki-facing text is shortened.

*CRITICAL RULE — every deck's exported file is a build artifact, not a
package file.* None of them are ever committed to the repo (gitignore
=.agents/flashcards/*/anki-export.txt=) — each is fully regenerable from its
own =deck.org= at any time, the same reason a compiled binary doesn't belong
in version control. What's authored and versioned here is the
source-of-truth card content; what Anki does with it locally (scheduling
state, review history, the memory-model parameters FSRS fits to you
specifically) is genuinely personal data, not project documentation, and has
no reason to ever enter this repository.

* Anki Setup (one-time, local)

Not something this repo governs — noted here only so the exported file is
actually usable once produced:
- Enable the FSRS scheduler in Anki's deck options. Confirm the exact toggle
  location against Anki's current manual before relying on this line — UI
  details drift across releases, and this guide's own citation-integrity
  rule above applies to itself too.
- Set a target retention (Anki's FSRS setting for the probability of
  recalling a card when it's due). No specific number is prescribed here —
  pick one and adjust it based on how review load actually feels once real
  decks are being reviewed, rather than treating a borrowed number as
  authoritative for this project's own content.
- Import a deck's =anki-export.txt= (=File > Import=) after each export run
  for that deck — one import per deck you've touched, not a single combined
  import.

* Study Session Workflow

Reviewing a due card can happen with an AI as a live study partner — this
agent, or a different one entirely, any provider (same "who's driving
matters, not which chat window is open" principle as
=02-expansion-guide.org='s External Session Workflow). Anki stays the sole
system of record for what got scheduled and how a review went; a study
session never edits =deck.org=, never edits Anki's own database on the AI's
behalf, and produces no repo file at all. That's a deliberate simplification
compared to the walkthrough system's own External Session Workflow: there,
an external session's claims have to be reconciled back into a real
=*Result:*= block before anything counts as done. Here, there's nothing to
reconcile — Anki's review log already *is* the durable record, exactly as
Export Workflow's own CRITICAL RULE already establishes; a study session's
job is only to grade a single answer in the moment.

** Workflow

1. Open the deck in Anki as normal. Anki's own FSRS scheduler decides what's
   due — not this guide, not the AI.
2. Read the card Anki shows you. Its front carries a short, muted =[xxxxxxxx]=
   prefix (see Export Workflow) — tell the AI that ID, *before* flipping the
   card to see the back.
3. Answer the AI in your own words, from memory — not by reading the back of
   the card first. Attempting the recall is the entire point; flipping first
   and then "answering" just narrates what you already see.
4. The AI looks up the card (=SCRIPTS/find-card.py <id>=, or reading
   =.agents/flashcards/<uuid>/deck.org= directly if it already has repo
   access) and grades your answer against the card's own =*Back:*= or cloze
   content, using the same administering discipline
   [[file:03-quiz-guide.org][03-quiz-guide.org]]'s "Administering a Quiz"
   section already establishes — ground a hint in the card's own captured
   =*Source:*= step rather than an abstract restatement, bound retries to one
   hint and one retry, then explain and move on. That section is the single
   source of truth for how to run this kind of live grading; this workflow
   doesn't restate its rules, just reuses them at the single-card grain
   instead of the five-question grain.
5. The AI suggests which of Anki's four ratings fits — Again, Hard, Good, or
   Easy, per the =For AI Assistants= boilerplate's own breakdown (Deck
   Template, above) — based only on what happened in the conversation (was a
   hint needed, did you hedge or self-correct), since it has no way to
   observe hesitation or timing the way Anki itself does.
6. Flip the card in Anki and rate it yourself. The AI's suggestion is input,
   not a verdict — you know whether it actually felt easy or hard better
   than a transcript does, so the final button is always your call.
7. Repeat for the next due card.

*CRITICAL RULE — the AI must not reveal the back before you've answered.*
Looking up a card necessarily means the AI already has the =*Back:*=/cloze
answer in hand; the discipline is behavioral, not something a script
enforces — exactly like this system already trusts an AI not to blurt out a
Quiz's Answer Key before the human attempts a question. Ask first, grade
second.

* index.org Conventions

- One line per deck: a =file:= link to =<uuid>/deck.org=, the walkthrough
  title, card count.
- A separate list of archived walkthroughs with no deck directory yet — this
  is the actual to-do list for "finish mining the archive," and
  =validate-flashcards.py= keeps it honest (see below).
- Grouped by Domain/Subcategory as the deck count grows, same convention as
  [[file:../wikis/index.org][the wiki's own index.org]].

* What the Validator Checks

=SCRIPTS/validate-flashcards.py= runs as its own pass, separate from
=validate-walkthroughs.py= — run both after any change here, since each
builds its own UUID registry independently and neither catches a
cross-script collision by reading alone, only by comparing. It checks:
- Every card's =:ID:= is a valid UUID, registered into the same cross-system
  collision namespace as every walkthrough, wiki, and index UUID (see UUID
  Placement, above).
- Every card's =*Source:*= link resolves to the deck's own source walkthrough,
  =.agents/walkthroughs/archive/<uuid>.org=.
- Every =TYPE: cloze= card contains at least one valid =\{\{c\d+::...\}\}=
  span; every =TYPE: basic= card has a non-empty =*Back:*=.
- Every =.agents/flashcards/<uuid>/= directory name is a valid UUID matching
  a =DONE= node in
  [[file:../index.org][=.agents/walkthroughs/index.org=]] whose walkthrough
  is archived — same check =04-archive-guide.org= already applies to
  =archive/<uuid>.org= itself. A deck directory with no =deck.org= inside it
  is also a failure.
- Every deck is listed in =.agents/flashcards/index.org= — an unlisted deck
  is exactly the kind of orphan this system's sibling guides already forbid.
- Every =deck.org= has a =* For AI Assistants= section — same required-section
  enforcement =validate-walkthroughs.py= already applies to
  =walkthrough.org='s own section of that name, so a deck dragged into a
  different AI chat is never missing the context that makes it portable.
- (Warning, not failure) any archived walkthrough with no matching deck
  directory yet — a loose signal that mining hasn't reached it, not a hard
  rule about when it must.

* Best Practices

1. One card, one atomic fact or mechanism — never a card whose =*Back:*=
   requires remembering three unrelated things.
2. Pick Basic vs. Cloze deliberately per card, per the CRITICAL RULE in
   Authoring Workflow — don't default to whichever is faster to type.
3. Reword away from the walkthrough's own exact phrasing wherever plausible;
   cue dependency defeats the entire reason this feature exists.
4. Never invent a =*Source:*= citation from memory — open the archived file
   and confirm the fact is actually there before writing the card, same
   discipline =02-expansion-guide.org= requires when reusing any citation.
5. Run both validators after any change to a deck or
   =.agents/flashcards/index.org=.
6. Treat mining the archive as incremental, the same way expanding
   =index.org= issues into walkthroughs is incremental — there is no
   obligation to cover every archived walkthrough immediately.
7. During a Study Session, grade from memory, not from a re-read of the
   card's back — both the human answering and the AI grading exist to make
   retrieval effortful; skipping that by reading ahead defeats the entire
   reason spaced retrieval works.
8. Re-export a deck (=SCRIPTS/export-anki.py=) and re-import it into Anki
   whenever its =deck.org= changes — an out-of-date Anki collection is
   missing the visible id prefix or content a Study Session depends on for
   newly-mined cards.

#+TITLE: Walkthroughs CONTEXT Directory Guide

This guide details how =.agents/walkthroughs/CONTEXT/= is used: a
staging area for raw research material that later becomes filed issues
in [[file:../index.org][index.org]]. See
[[file:00-conventions.org][00-conventions.org]] for conventions shared
across this whole system, and
[[file:01-index-guide.org][01-index-guide.org]] for how a CONTEXT file's
material actually turns into a Level 3 issue.

CONTEXT is organized as one subdirectory per owning issue,
=CONTEXT/<issue-uuid>/= — the same UUID as that issue's own
[[file:../index.org][index.org]] node and, once expanded, its
walkthrough package directory — mirroring the same one-directory-per-issue
shape a walkthrough package already uses. Every research file that exists
because of a given issue lives together in that issue's own subdirectory,
never loose at =CONTEXT/='s top level.

CONTEXT holds raw, unsorted material on its way to becoming something
else — an issue, and later a walkthrough, whose own archived record
(see [[file:04-archive-guide.org][04-archive-guide.org]]) is what settles
into durable history once the work is done. A CONTEXT file that never
produces anything should not linger indefinitely (see Naming &
Lifecycle, below).

* Two Directions

Material reaches CONTEXT from two directions that carry different trust
levels, and must not be conflated:

- *You → agent (user-sourced).* You write or paste something yourself —
  your own reflection, an article you found, a report you generated
  elsewhere. Choosing to put it in CONTEXT is itself your approval; the
  agent can mine it directly into filed issues.
- *Agent → you (agent-sourced).* The agent goes looking for material on
  its own initiative — a Discover-Sources-style web research step,
  modeled on how Google NotebookLM proposes sources for you to accept
  rather than adding them unasked. The agent has not verified any of it
  actually fits your situation, so it carries a lower trust level until
  you say otherwise.

* The Context Index

*CRITICAL RULE — CONTEXT files are never edited to carry their own
metadata.* A CONTEXT file is raw material — it stays exactly as written
or dropped in, byte for byte. Every file's =:ID:=, =:SOURCE:=, and
=:STATUS:= live instead in a sibling file scoped to that file's own
owning issue, =.agents/walkthroughs/CONTEXT/<issue-uuid>/index.org=, one
entry per research file *belonging to that issue*:

#+begin_src org
* <Short, semantic title — what this material actually is>
  :PROPERTIES:
  :ID:       <uuid>
  :SOURCE:   you
  :STATUS:   approved
  :END:
  - *File:* [[file:<uuid>.<ext>][<uuid>.<ext>]]
  One or two sentences on what this material is.
#+end_src

The heading is a short, human-readable title, never the UUID itself — same
"never in visible text" rule as every other node in this system
(00-conventions.org's UUID Convention). The =:ID:= already gives the entry
its permanent, linkable identity; the heading's only job is to let a human
scanning that issue's own =index.org= tell its entries apart at a glance.

- =:ID:= — the file's permanent id. Generated the same way as every other
  UUID in this system (see 00-conventions.org's UUID Convention:
  =uuidgen=, never hand-typed) and, per Naming & Lifecycle below, is also
  the file's own filename.
- =:SOURCE:= — =you= or =agent=, per Two Directions above.
- =:STATUS:= — one of three values, tracking where the file sits between
  arriving and being used:
  - =proposed= — agent-sourced, found, not yet reviewed by you. *Never*
    valid on a =SOURCE: you= entry — putting a file in CONTEXT yourself
    already is the approval, so a user-sourced entry starts at =approved=
    and skips =proposed= entirely.
  - =approved= — cleared to mine, not yet cited by any filed issue. The
    starting state for every =SOURCE: you= entry; the state an
    agent-sourced entry reaches once you've said which parts land.
  - =mined= — at least one filed issue in =index.org= now cites this
    file.

*CRITICAL RULE — no filing without your go-ahead.* An issue must never
cite a =STATUS: proposed= file. When the agent brings in research on its
own initiative, it presents the findings and stops — nothing gets filed
until you say which parts actually apply. This is the gate that makes
agent-initiated research safe to use at all: the agent can find
generically-good material, but only you know what actually fits your
situation. A =SOURCE: you= entry has no such gate, since it starts at
=approved= already.

* Naming & Lifecycle

*CRITICAL RULE — which subdirectory a file goes in is never a choice.*
A CONTEXT file always belongs to exactly one issue — the one it's being
researched for — and lives at
=CONTEXT/<owning-issue-uuid>/<uuid>.<ext>=. If that issue's subdirectory
doesn't exist yet (its first-ever CONTEXT file), create it as part of
adding this one, the same way expanding an issue creates its walkthrough
package directory on first use (see
[[file:02-expansion-guide.org][02-expansion-guide.org]]'s Expansion
Workflow). A CONTEXT file's owning issue does not need to be expanded
into a walkthrough yet, or even to exist as anything beyond a filed
=index.org= node — research routinely happens before expansion.

*CRITICAL RULE — generic UUID filenames, generate never invent.* Every
CONTEXT file is named =<uuid>.<original-ext>= — the same UUID as its
entry's own =:ID:= in that issue's =index.org=, produced with =uuidgen=
(or the Python fallback in 00-conventions.org's UUID Convention), never
hand-typed. The extension stays whatever the material actually arrived
in (=.md=, =.txt=, =.org=, ...) — same reasoning as a SESH export never
being converted to =.org= (00-conventions.org changelog, v6): the file is
raw evidence, not a package artifact. A generic filename plus the
descriptive sentence in the index entry keeps the file itself
uninformative on its own, exactly like a walkthrough package directory
being a UUID rather than a slug.

This UUID shares the *same global namespace* as every other UUID in this
system — an index node, a walkthrough step. See 00-conventions.org's
UUID Convention, "one namespace" rule. Note this
means a CONTEXT file's own UUID is *not* the same as its owning issue's
UUID (the subdirectory name) — the subdirectory name identifies which
issue owns the files inside it, each file inside still gets its own,
separate, freshly-generated UUID.

A CONTEXT file that ends up cited by a filed issue (=STATUS: mined=)
stays — link integrity depends on it. An entry that never produces
anything — declined during approval, or user-sourced material that never
turned into an issue — should have its file deleted and its entry
removed from that issue's =index.org=, rather than left to accumulate.
Same instinct as [[file:01-index-guide.org][01-index-guide.org]]'s Best
Practice 3 (prune stale open issues). If that was the subdirectory's only
file, delete the now-empty subdirectory too.

* Workflow: Agent-Sourced Research

1. Search the web for real, current sources on the topic — do not rely
   on training-data recall dressed up as "research." Same principle as
   the UUID Convention's "generate, never invent" rule, applied to claims
   instead of identifiers.
2. Curate a small, focused set (not a link dump) into one CONTEXT file,
   named with a freshly generated UUID, placed in the owning issue's own
   =CONTEXT/<issue-uuid>/= subdirectory (created first if this is that
   issue's first CONTEXT file), with a one-line "why this is relevant"
   note per source — mirroring NotebookLM's Discover Sources annotations.
3. Add its entry to that subdirectory's own =index.org=: =:SOURCE: agent=,
   =:STATUS: proposed=.
4. Present the findings in conversation and stop. Do not create any
   issue in =index.org= that cites this file yet (see the CRITICAL RULE
   under The Context Index).
5. Once you've responded, flip the entry to =STATUS: approved= and file
   issues only for the parts you confirmed. After at least one issue
   cites the file, flip it to =STATUS: mined=.

* Workflow: User-Sourced Material

Material you've researched yourself is always auto-approved — no review
gate, since choosing to bring it in already is your approval — but *how*
it actually gets into a =CONTEXT/<issue-uuid>/= subdirectory now has two
forms:

- *Handed over directly in conversation* (a short paste, or something
  concrete enough to write up on the spot): the agent writes it straight
  into the owning issue's =CONTEXT/<issue-uuid>/= subdirectory, generates
  its UUID filename, and adds an entry to that subdirectory's =index.org=
  with =:SOURCE: you=, =:STATUS: approved=.
- *Handed over as a file, via =.agents/walkthroughs/inbox/=* — a
  genuinely separate workflow from agent-sourced research, covering
  format handling, issue-mapping (including filing a brand-new issue
  when nothing existing fits), per-file receipts, and deletion after
  ingestion. See
  [[file:10-ingestion-guide.org][10-ingestion-guide.org]] for the full
  procedure — this file doesn't restate it.

Either way, the entry lands in the same place and the agent mines it
directly into filed issues the same way any approved CONTEXT file does —
see The Context Index, above, for the =STATUS: mined= transition once at
least one filed issue cites it.

*CRITICAL RULE — grounding applies to both directions.* Every issue
description that states a claim drawn from research must trace back to
something actually written in a specific CONTEXT file — never
extrapolated from the agent's general knowledge and never presented as
specific to your situation when the source is generic background
material. This extends the same "don't trust the
file's own claims uncritically" discipline
[[file:02-expansion-guide.org][02-expansion-guide.org]]'s =For AI
Assistants= section already requires when *reading* a walkthrough, to
*writing* an issue from CONTEXT material in the first place.

* Checking Pending Files

=SCRIPTS/context-status.py= reads every =CONTEXT/<issue-uuid>/index.org=
and reports every entry that isn't =mined= yet, tagged by owning issue —
=proposed= entries waiting on your review, and =approved= entries cleared
to mine but not yet used. Run it any time CONTEXT feels like it's
accumulating faster than it's being worked through.

* Mining a File

Once you've said which parts of a CONTEXT file actually apply, the mining
step itself is two things: (1) actually write the citation — a
=[[file:...]]= link to the CONTEXT file — into whatever it's extending
(an =index.org= issue description, or a walkthrough's own Problem/Why/Notes),
along with whatever real content the research justifies, and (2) flip the
entry's =:STATUS:= to =mined= once that citation exists.

=SCRIPTS/context-mine.py <context-uuid> <citing-file>= automates step 2
only — it searches every =CONTEXT/<issue-uuid>/index.org= for the entry
matching =<context-uuid>=, refuses to run unless the citing file already
contains a real =[[file:...]]= link to that UUID, then flips that entry's
=:STATUS:= (in whichever subdirectory's =index.org= actually holds it)
and re-runs the full validator. It deliberately does *not* write the
citation or the mined content itself: deciding what the research actually
justifies adding, and writing it well, stays exactly as much a human (or
an agent working *with* the human) task as writing any other part of a
walkthrough — this script only removes the repetitive bookkeeping around
that decision, not the decision itself.

* Best Practices

1. One CONTEXT file, one scoped topic — don't let a single file answer
   more than one question, the same "a good notebook has a job
   description" principle NotebookLM's own guidance uses.
2. Prefer several small, focused files over one sprawling document; each
   is easier to cite precisely and easier to retire once mined.
3. When an issue's description draws on a CONTEXT file, mention which
   file in the issue body (a relative =[[file:...]]= link) so the
   citation is checkable, not just asserted.
4. Never let a =STATUS: proposed= entry sit forever unresolved — either
   review it and flip its status, or delete it and its entry if it turned
   out not to be worth pursuing. =SCRIPTS/context-status.py= is what
   surfaces these.
5. Run =SCRIPTS/validate-walkthroughs.py= after editing any
   =CONTEXT/<issue-uuid>/index.org= — it checks every entry has a valid,
   globally unique =:ID:=, a valid =:SOURCE:=/=:STATUS:=, a =file:= link
   that resolves, that no real CONTEXT file is missing its entry, and
   that the subdirectory itself is named after a real =index.org= node's
   UUID.

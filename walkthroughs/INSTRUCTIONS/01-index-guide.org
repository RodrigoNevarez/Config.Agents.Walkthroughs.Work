#+TITLE: Walkthroughs Index Maintenance Guide

This guide details how to create, structure, and maintain
[[file:../index.org][index.org]], the entry point for this
repository's *walkthroughs*: teaching artifacts that document how a
real problem was solved, written so the solving builds the human's own
understanding instead of leaving them dependent on the agent for the
next similar problem. See
[[file:02-expansion-guide.org][02-expansion-guide.org]] for how an
individual topic gets expanded into a full walkthrough package,
[[file:08-context-guide.org][08-context-guide.org]] for how raw research
material in =.agents/walkthroughs/CONTEXT/= becomes a filed issue here in
the first place, and [[file:00-conventions.org][00-conventions.org]] for
the issue-tracker mental model and UUID rules both guides share — this
file only covers what's specific to =index.org= itself.

Walkthroughs are not scoped to any one project or repository's setup
— a topic can be anything worth documenting this way. =index.org= is
where every topic lives, expanded or not; the actual write-ups live
alongside it as per-topic packages.

* Index Structure & Hierarchy

The index is Org-mode, organized hierarchically so related issues stay
discoverable — this grouping is just for navigation, the way a tracker
groups issues by project or milestone; it isn't what determines state:

- *Level 1 (=*=)*: broad domains (e.g. =Environment & Tooling=,
  =Software Engineering=). Add new domains as they come up — the index
  is not limited to any fixed set.
- *Level 2 (=**=)*: subcategories within a domain.
- *Level 3 (=***=)*: an individual issue/topic. This is the node that
  carries the =TODO=/=ACTIVE=/=DONE= state (see
  [[file:00-conventions.org][00-conventions.org]]'s Issue-Tracker Mental
  Model) and the =:ID:= property, and, once expanded, the link to its
  walkthrough package.

** The UUID Placement Rule
Every Level 3 node MUST include a =:PROPERTIES:= drawer containing a
unique =:ID:=, which becomes the name of the topic's package directory
once it's closed (see
[[file:02-expansion-guide.org][02-expansion-guide.org]]). See
[[file:00-conventions.org][00-conventions.org]]'s UUID Convention
section for the generation and placement rules — same rules, one
place, shared with the walkthrough packages themselves.

** The Blocked By Property

Alongside =:ID:=, a Level 3 node may also carry a =:BLOCKED_BY:= — zero
or more UUIDs, space-separated, each naming another Level 3 node, in
=index.org= or in =CONTEXT/closed.org= (see Closed Issues, below), that
must genuinely be true (built, decided, merged)
before this one can even start. Absence means exactly what it looks
like: nothing currently known blocks it, and it can be worked today.
This is a real dependency graph, not a single linear sequence — two
issues can be mutually independent (neither blocks the other) and both
still block a third, something one flat ordering could never express.

This exists for the same reason a linear build order once did:
walkthroughs "are not scoped to any one project or repository's setup"
(this guide's own intro) — the index for one project doubles as a
reusable template for the next similar one. A real dependency graph is a
*better* template than a flat sequence ever was, since it records the
actual structural prerequisites a future project needs to satisfy, not
just one arbitrary linearization of them.

*CRITICAL RULE — a =DONE= node's =:BLOCKED_BY:= is permanent; a =TODO= or
=ACTIVE= node's is not.* Once a node closes (=DONE=, fully worked), its
=:BLOCKED_BY:= is a historical
record of what actually had to be true first — never edited afterward,
same reasoning as archived walkthrough packages never being rewritten
(see [[file:04-archive-guide.org][04-archive-guide.org]]). An open
node's =:BLOCKED_BY:= is a live understanding of what's actually in the
way right now, and gets rewired freely as that understanding changes —
adding an edge when a real prerequisite surfaces, removing one once it's
satisfied or turns out not to matter — without needing to touch anything
else in the graph. This is strictly easier than the flat-sequence
renumbering discipline it replaces: a node with nothing depending on it
can be inserted, moved, or removed without disturbing any other node's
position relative to anything but its own direct blockers.

*CRITICAL RULE — every =:BLOCKED_BY:= UUID must resolve to a real node,
and the graph must be acyclic.* A UUID that doesn't match any node in
=index.org= is a dangling reference — usually the result of pruning an
issue (Best Practice 3, below) without also removing it from whatever it
was blocking. A cycle (=A= blocked by =B= blocked by =A=) is a
contradiction, not just untidy: nothing inside a cycle could ever
legitimately start. =SCRIPTS/validate-walkthroughs.py= checks both
mechanically.

*CRITICAL RULE — pruning an issue means removing it from every
=:BLOCKED_BY:= that names it, not just deleting its own node.* Grep for
its UUID across =index.org= before deleting the node itself — the same
"remove every link that points at a file you're about to delete"
discipline [[file:04-archive-guide.org][04-archive-guide.org]] already
applies to archiving.

A node with an empty or absent =:BLOCKED_BY:= is *ready* — nothing known
stands between it and being worked today. A node with one or more
unsatisfied =:BLOCKED_BY:= entries (any pointing at a node that isn't
=DONE= yet)
isn't ready yet — that's the whole point of writing the edge down
instead of discovering the gap mid-work.

** The Blocked Property

Every Level 3 node also carries =:BLOCKED: true= or =:BLOCKED: false= in
its =:PROPERTIES:= drawer, directly after =:BLOCKED_BY:= (or after =:ID:=
when there are no blockers). It answers the question the paragraph above
defines, "can this be started today?", in one readable place, so nobody
has to chase each blocker UUID and look up its state.

- =TODO= or =ACTIVE= node: =true= if any UUID in its =:BLOCKED_BY:=
  names a node that isn't =DONE= yet; =false= otherwise, including when
  it has no blockers.
- =DONE= node: always =false=, because a fully worked issue isn't waiting
  on anything.

An =ACTIVE= blocker still blocks. Its walkthrough exists, but until its
checklist is fully worked, whatever depends on it can't rely on its
result being real. That's the reason =DONE= means worked rather than
written.

*CRITICAL RULE — =:BLOCKED:= is derived, never hand-edited.* The source of
truth is =:BLOCKED_BY:= plus each node's =TODO=/=ACTIVE=/=DONE= state;
=:BLOCKED:= only mirrors them. Any edit that changes either one (filing
an issue, rewiring an edge, pruning a node, expanding or closing an issue) changes
some =:BLOCKED:= values, so regenerate them all with:
#+begin_src sh
python3 .agents/walkthroughs/SCRIPTS/sync-index.py
#+end_src
=sync-index.py= owns every *derived* value in one pass: each active
walkthrough's =[x/n]= count and =TODO=/=DONE= heading (counted from its real
checkboxes), each issue's =ACTIVE= ↔ =DONE= state (following that
checklist), and every =:BLOCKED:=. It prints one line per change
(=CLOSED=, =NEWLY READY=, =NOW BLOCKED=, ...) and nothing at all when
everything is current, so running it after any edit costs almost
nothing to read. =--list= also prints every open issue as ready or
blocked. =--check= writes nothing and exits non-zero if anything is out of
date. =SCRIPTS/validate-walkthroughs.py= fails on the same
inconsistencies, so a forgotten sync fails validation instead of silently
misleading anyone. It never expands an issue (=TODO= → =ACTIVE=), archives,
checks a box, or edits an archived =outcome.org=; those are deliberate
acts, not bookkeeping. A stale =false= is the dangerous direction: it sends someone to
start work whose prerequisite isn't there yet.

** Issue States
- *Filed (=TODO=)*: heading + =:ID:= drawer + a =*End-State:*= line (see
  Backward-Chained Filing, below) + a short description of the problem,
  with no walkthrough link yet. This is a filed issue — something worth
  documenting the next time it's actually solved.
- *Expanded (=ACTIVE=)*: the same node, plus a =- *Walkthrough:*
  [[file:<uuid>/walkthrough.org][...]]= line pointing at its package
  directory. The walkthrough exists; its checklist isn't fully worked.
- *Closed (=DONE=)*: the walkthrough's checklist is fully worked
  (=[n/n]=). The Walkthrough link stays. Once the walkthrough is archived
  (see [[file:04-archive-guide.org][04-archive-guide.org]]), the whole node
  leaves =index.org= for =CONTEXT/closed.org= (see Closed Issues, below).

Don't force every issue open today to be expanded or closed immediately. Filing a
topic costs nothing; writing the full walkthrough is worth doing only
when the problem is actually being worked through.

** Closed Issues

=index.org= is the working set: open issues (=TODO=, =ACTIVE=) plus any
=DONE= issue whose walkthrough hasn't been archived yet. An archived
issue's node moves, unchanged apart from rebased =file:= links, to
=.agents/walkthroughs/CONTEXT/closed.org=. That's the same move archiving
already makes for the walkthrough itself: a settled issue's research,
outcome, and index entry all end up under =CONTEXT/=. =closed.org= uses the
same =* Domain= / =** Subcategory= headings, created there as needed.
A subcategory or domain that the move leaves empty in =index.org= is
removed.

Nothing about the issue is lost, which is why this beats pruning:
- =:BLOCKED_BY:= edges from open issues still resolve, because
  =SCRIPTS/validate-walkthroughs.py= and =SCRIPTS/sync-index.py= read both
  files as one issue namespace.
- The issue's =CONTEXT/<uuid>/= folder still matches a node, as the
  validator requires.
- The permanent =:BLOCKED_BY:= record and the Walkthrough link to
  =outcome.org= stay intact.

*CRITICAL RULE — the move is bookkeeping, done by =SCRIPTS/sync-index.py=,
never by hand.* After archiving, run it. It moves every =DONE= node whose
=CONTEXT/<uuid>/outcome.org= exists, rebases its links for the
=CONTEXT/= directory, and prints =MOVED TO CLOSED=. The validator enforces
the split both ways: an archived issue still in =index.org= fails, and so
does anything in =closed.org= that isn't an archived =DONE= issue. A
correction to a closed issue is a new issue in =index.org=, never an edit
that drags the closed one back (see 04-archive-guide.org's Purpose).

* Handling a Pivot

A project's own purpose sometimes changes mid-stream — a new requirement
supersedes an old one, an approach gets abandoned, priorities get
reshuffled. Treat that as an explicit checkpoint on =index.org= itself
the moment it happens, not just a rule to remember while filing whatever
issue comes next:

1. *Review every open (=TODO=) node* against the new direction. One that
   no longer matters gets pruned (Best Practice 3, below — remember to
   remove it from every =:BLOCKED_BY:= that names it too); one that
   still matters but the new direction changes what's actually in its
   way gets rewired, not left pointing at a blocker that no longer
   applies.
2. *Rewire =:BLOCKED_BY:= edges to match the new understanding* — add an
   edge for a prerequisite the pivot introduces, remove one that no
   longer holds. Never touch a =DONE= node's =:BLOCKED_BY:= while doing
   this; the pivot changes what's still ahead, not what already
   happened.
3. *File whatever new issues the pivot introduces*, working backward
   from the new end-state — see Backward-Chained Filing, below.
4. *Regenerate =:BLOCKED:= and run the validator* once the dust
   settles, same as any other edit to =index.org= (see The Blocked
   Property, above).

Skipping this checkpoint is how an index quietly goes stale — the
dependency graph keeps existing, but stops describing what's actually in
the way of anything, which defeats its whole purpose.

* Backward-Chained Filing

When filing more than one new issue at once — a pivot, a new feature
area, anything that isn't a single isolated fix — start from the
end-state and work backward, not forward from whatever's already in
front of you. Forward-filed issues describe what to build next, in
whatever order occurs to you; worked backward from a defined end-state,
each issue instead answers a sharper question — *what has to be real
before this one can even start* — which is exactly the information
=:BLOCKED_BY:= needs to be worth anything.

1. *State the end-state as its own issue first* — the =*End-State:*=
   line is the precise condition that means this whole effort is
   actually done, not a description of the work.
2. *Ask, recursively: what's the immediate thing that has to be true
   before this issue could even start?* File that as a separate issue,
   and set the first issue's =:BLOCKED_BY:= to point at it.
3. *Repeat on the new issue*, walking backward, until the honest answer
   is "nothing — this can start against the project as it exists right
   now." That issue gets no =:BLOCKED_BY:= — it's the root, ready to
   work today.
4. *Wire the edges as you go, not after the fact* — every issue in the
   chain except that root should come out of this process with a
   non-empty =:BLOCKED_BY:= pointing at whatever you just filed to
   unblock it.

This is deliberately not a forecasting exercise — don't invent
hypothetical future blockers for a simple, single-issue fix. It's for
the case where you already know there's real structure here, and filing
forward would just mean discovering the missing prerequisite mid-work
instead of before starting.

* Linking & Navigation

- Link to a topic's package from the index with a relative =file:=
  link: =[[file:<uuid>/walkthrough.org][Topic Title]]=.
- Link between two walkthrough packages (sibling directories) by
  stepping up one level first: =[[file:../<other-uuid>/walkthrough.org][...]]=.
- Link from a walkthrough back to something elsewhere in the
  repository using a relative path from inside its package directory
  (e.g. three levels up to reach the repo root: =../../../docs/...=).

* Best Practices

1. *Use relative paths* for every link, so the whole tree stays
   portable.
2. *Keep the hierarchy shallow but real* — don't invent Level 2
   subcategories with only one topic in them; don't flatten a genuinely
   broad domain into one bucket either. Use tags, not new
   subcategories, for a topic that cuts across more than one.
3. *Prune stale open issues* — if a filed topic turns out not to be
   worth documenting, remove it rather than letting the index
   accumulate dead entries. Remove it from every =:BLOCKED_BY:= that
   named it too (see The Blocked By Property, above) — a dangling
   reference is a hard validator failure, not just untidy.
4. *Consistent naming*: heading text should be the same imperative,
   specific problem statement used as the =#+TITLE:= of the closed
   issue's =walkthrough.org=.
5. *Run the validator* after editing =index.org= —
   =SCRIPTS/validate-walkthroughs.py= checks every node has a valid,
   unique =:ID:=, that every =:BLOCKED_BY:= UUID resolves to a real node
   with no cycles, that every =:BLOCKED:= value is present and current
   (run =SCRIPTS/sync-index.py= first; see The Blocked Property),
   that ACTIVE and DONE nodes have a matching package or outcome, that
   the state agrees with the checklist count (=DONE= only at =[n/n]=),
   and that TODO nodes don't. It catches exactly the mistakes the
   CRITICAL RULEs above are trying to prevent, mechanically instead of
   by memory.
6. *Write the =*End-State:*= line as a condition, not a task* — "the
   webhook handler is idempotent under duplicate delivery," not "add
   idempotency to the webhook handler." The first is checkable; the
   second just restates the heading. Not mechanically checked (like the
   walkthrough's own =*Why:*= line quality) — it's worth the discipline
   anyway, since a vague end-state produces a vague =:BLOCKED_BY:= graph.
7. *Add =*Anti-Goals:*= only when scope is genuinely ambiguous* — a
   short list of "explicitly not this" lines, directly under
   =*End-State:*=, for an issue big or vague enough that a future
   expansion (see [[file:02-expansion-guide.org][02-expansion-guide.org]])
   could plausibly scope-creep. Most issues don't need this; a one-line
   fix has no ambiguous scope to contain.
8. *Don't wire a =:BLOCKED_BY:= edge you're not sure about* — an
   incorrect edge is worse than a missing one: a missing edge just means
   the graph doesn't yet know about a real constraint (discoverable once
   you actually start the work), while an incorrect edge actively stops
   a ready issue from looking ready. When genuinely unsure, leave it
   unwired and note the uncertainty in the issue body instead.

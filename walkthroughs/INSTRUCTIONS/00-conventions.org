#+TITLE: Walkthrough Shared Conventions
#+WALKTHROUGH_GUIDE_VERSION: 20

Single source of truth for conventions shared by
[[file:01-index-guide.org][01-index-guide.org]] (the index),
[[file:02-expansion-guide.org][02-expansion-guide.org]] (walkthrough
packages), [[file:04-archive-guide.org][04-archive-guide.org]]
(archiving a settled package), [[file:05-wiki-guide.org][05-wiki-guide.org]]
(the project wiki at =.agents/wikis/=),
[[file:07-code-suggestions-guide.org][07-code-suggestions-guide.org]]
(suggesting code inside a =[you-run]= step without writing it into the repo),
and [[file:08-context-guide.org][08-context-guide.org]] (the research
staging area at =.agents/walkthroughs/CONTEXT/=). All six reference this
file instead of restating it — a rule here changes in exactly one place,
not several that can drift apart. Checked mechanically by
=SCRIPTS/validate-walkthroughs.py= (walkthroughs, index, and wiki).

* UUID Convention

Every linkable node in this system — an index issue, a walkthrough
step — gets a permanent =:ID:= via a =:PROPERTIES:= drawer:

#+begin_src org
:PROPERTIES:
:ID:       <uuid>
:END:
#+end_src

- *CRITICAL RULE — generate, never invent.* Produce the UUID with a
  real generator: =uuidgen=, or =python3 -c 'import uuid;
  print(uuid.uuid4())'= if that's unavailable. Never hand-type a
  UUID-shaped string. An LLM-typed "plausible" UUID isn't actually
  random and risks colliding with one already in use.
- *CRITICAL RULE — never in visible text.* The UUID lives strictly
  inside the drawer — never in a heading, never in a checklist item's
  own text. Headings and step descriptions stay clean and
  human-readable.
- *CRITICAL RULE — one namespace.* Every UUID under
  =.agents/walkthroughs/= *or* =.agents/wikis/= — index nodes, package
  directory names, individual walkthrough steps, wiki pages (see
  [[file:05-wiki-guide.org][05-wiki-guide.org]]'s UUID Placement), and
  CONTEXT file entries (see
  [[file:08-context-guide.org][08-context-guide.org]]'s Naming &
  Lifecycle) — must be globally unique across both trees, not just within
  one file. Run =SCRIPTS/validate-walkthroughs.py= to check.

* Issue-Tracker Mental Model

Every Level 3 node in [[file:../index.org][index.org]] is an *issue*:
title (heading), body (short description), state (=TODO=/=DONE= via
Org's native keyword — open vs. closed), optional tags (Org's
=:tag:= syntax, standing in for labels), and id (the =:ID:= UUID
above, standing in for an issue number). Closing an issue means
expanding it into a walkthrough package — see
[[file:02-expansion-guide.org][02-expansion-guide.org]]. There's no
"resolved but undocumented" state: closed implies the write-up exists.

* Guide Version

=#+WALKTHROUGH_GUIDE_VERSION:= at the top of this file is the current
version of the required =walkthrough.org= structure. Every
=walkthrough.org= must carry a matching
=#+WALKTHROUGH_GUIDE_VERSION:= line directly under its =#+DATE:=.

*This version number gates =walkthrough.org='s own required structure
only.* =.agents/wikis/= (see [[file:05-wiki-guide.org][05-wiki-guide.org]])
is a separate system with its own validator checks, enforced
unconditionally rather than version-gated — a wiki page doesn't declare a
=#+WALKTHROUGH_GUIDE_VERSION:= line and isn't subject to this section's
staleness warning. Introducing =05-wiki-guide.org= itself did not bump this
version, for that reason.

Bump the number here whenever the required structure actually changes
— a section added, removed, or renamed, or a new CRITICAL RULE that
changes what "valid" means. Existing walkthrough packages are *not*
required to be retrofitted immediately when the version bumps — that
would make every structural change a repo-wide scramble. Instead, a
walkthrough's version number falling behind current is exactly the
signal that it may now be missing something the guide requires;
=SCRIPTS/validate-walkthroughs.py= reports this as a warning, not a
failure, so staleness stays visible instead of silent.

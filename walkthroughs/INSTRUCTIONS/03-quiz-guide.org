#+TITLE: Walkthrough Quiz Guide
#+DATE: 2026-08-21

Single source of truth for writing and running a walkthrough's =* Quiz=
section, referenced by
[[file:02-expansion-guide.org][02-expansion-guide.org]] instead of
restating it — the same "one place, not two that can drift apart"
principle as [[file:00-conventions.org][00-conventions.org]].

* Purpose

The Quiz is retrieval practice, not a comprehension check pasted at the
end for form's sake: answering from memory, unprompted, is what makes
understanding stick — re-reading the walkthrough doesn't. It's also the
only part of this system that tests whether the *why* actually landed,
rather than whether the checklist got followed.

* Authoring a Quiz

*CRITICAL RULE — do not write the Quiz until the Guide checklist is fully
checked.* Write it only after every step in =walkthrough.org='s Guide has a
real =*Result:*= block — never at expansion time, alongside the Problem and
Guide sections. The person (or AI) writing a fresh walkthrough has usually
already done real research before writing a single word of it — that's
where the Problem section and each step's =*Why:*= come from. If the Quiz
gets written in that same pass, the author already knows what the steps
will find, and the questions and Answer Key end up quietly encoding that
predetermined answer. The live Quiz session then stops being retrieval
practice and becomes reconstructing what the author already wrote down —
the exact failure mode this guide's own Purpose section exists to prevent.
Write the Quiz as the *last* thing added to a package, once there's a real,
reached decision to test understanding of, not a predicted one.
=SCRIPTS/validate-walkthroughs.py= enforces this both directions for a
package declaring guide v9+: a =* Quiz= section is a hard failure if
present while the checklist isn't fully checked, and is required (same
count rules as always) once it is. A package still declaring an older
version is not retroactively required to follow this — it keeps the
version-staleness warning instead, per
[[file:00-conventions.org][00-conventions.org]]'s non-retroactive policy.

A =* Quiz= heading with exactly five open-ended questions, plus a
=** Answer Key= subsection with exactly five answers —
=SCRIPTS/validate-walkthroughs.py= counts both and fails on anything else.

*CRITICAL RULE — open-ended only, never yes/no or multiple-choice.* "Did
editing =PS1= require sourcing =.bashrc=?" is a coin flip that can be
guessed without understanding anything. "Why does editing =.bashrc= have
no effect until the shell is reloaded?" forces an actual explanation to
answer at all.

*CRITICAL RULE — test the mechanism, not the memory.* A good question
survives being asked about a slightly different, unfamiliar scenario (e.g.
"if a *different* dotfile had this same symptom, how would you diagnose
it?"). If the only way to answer is to have memorized this exact
walkthrough's wording, rewrite the question. Write against the Mental
Model level, not exact syntax — a question that only checks whether
someone remembers a flag name tests recall of trivia, not understanding.

Include the =** Answer Key= subsection below the questions, under its own
subheading so a reviewer can attempt their own answer before checking it,
instead of the answer sitting right next to the question. It should be
grading guidance — what a correct answer must cover — not necessarily the
exact wording a human would say back.

*Merge-gating rule:* if a pull request exists because someone followed
this walkthrough to fix or build something, treat it as not mergeable
until the author answers all 5 questions correctly — reviewer asks, author
answers in their own words, reviewer checks against the Answer Key. This
is what makes "I followed the walkthrough" and "I understood the
walkthrough" distinguishable before the change lands.

* Administering a Quiz

Running the Quiz well is its own skill, separate from writing good
questions — this section exists because an actual live quiz session
surfaced gaps this guide didn't originally cover.

** Ask one question at a time

Present a single question, wait for a real answer, grade it, *then* move
to the next. Don't dump all 5 up front — that turns retrieval practice
into an open-book test, since later questions leak context that makes
earlier ones easier to guess at.

*CRITICAL RULE — ground hints in the walkthrough's own captured evidence.*
When an answer misses, the first hint must point at real evidence already
captured in the file — a step's own =*Result:*= block, its raw
request/response payload, its actual command output — not an abstract
restatement of the question. An abstract hint ("what would go wrong
without it?") can fail for a reason that has nothing to do with reasoning
ability: the person may simply not remember what a term in the question
even refers to. Pointing back at their own captured output re-grounds them
in something concrete they already produced, instead of asking them to
reason in the abstract a second time. In practice this was the single most
effective intervention: an abstract hint left the person stuck on "I don't
remember what a capability list is"; re-pasting their own captured
=initialize= JSON from an earlier step un-stuck it immediately.

*CRITICAL RULE — bounded hint-and-retry, not indefinite looping.* One
grounded hint, one retry. If the retry is still wrong, or the person is
still unsure, explain the mechanism plainly and move on — don't keep
circling the same question hoping for a different answer, and don't
silently mark a wrong answer correct just to keep things moving either.
Both failure modes defeat the point: rubber-stamping teaches nothing, and
an unbounded loop turns a quiz into an interrogation.

** Grade the actual answer, not just pass/fail

Real answers rarely split cleanly into right/wrong. Distinguish:
- *Correct* — confirm it, and add any refinement worth having (e.g. a
  right conclusion reached via slightly the wrong framing).
- *Correct but thin* — confirm it, then fill in the part they didn't
  mention, so the fuller picture ends up on record even though the core
  landed.
- *Right direction, wrong specifics* — don't just say "no"; apply the
  grounded-hint rule above before re-asking, rather than re-explaining the
  question in the abstract.
- *Confidently wrong* or *stuck/no idea* — both get the same
  ground-and-retry treatment, but a flat "I don't know" is a signal to
  reground immediately rather than trying a second abstract hint first.

** Record the outcome

*CRITICAL RULE — the quiz result belongs in the walkthrough's Notes, not
just in the conversation.* Record which questions were answered cleanly
and which weren't — a bare "passed" or a score fraction throws away the
only useful part. A future reader (human or AI, possibly during a
=#+LAST_REVIEWED:=-triggered refresher — see the =For AI Assistants=
section in [[file:02-expansion-guide.org][02-expansion-guide.org]]) needs
to know *which* question to re-probe, not just that a quiz happened. Note
the date and whether it ran live with the director or was self-administered
in an external session (see the
[[file:02-expansion-guide.org][External Session Workflow]] — a
closed-question self-check quiz run there is still not a substitute for
this one; see that file's CRITICAL RULE on the distinction).

Example:
#+begin_src org
- *Quiz result* (2026-08-21, run live with the director): 4/5 landed
  correctly on the first or second attempt. *Q3 is the real gap*: "<short
  restatement of what didn't land>" did not land even with a grounded
  hint — required a full explanation. Flagging for a refresher check next
  time this package is reviewed.
#+end_src

* Best Practices

1. One question at a time, real answer, real grade — never batch-present
   all 5 and grade them together.
2. A hint's first move is always back into the file's own captured
   evidence, never a fresh example invented on the spot.
3. Bound the loop: one hint, one retry, then explain and move on.
4. Record outcomes with enough specificity that a future reviewer knows
   what to re-probe, not just whether it passed.
5. A closed-question self-check quiz from an external session
   ([[file:02-expansion-guide.org][External Session Workflow]]) is
   supplementary practice only — never grade the real Quiz from it, and
   never let it substitute for actually asking the 5 questions here.
6. Write quiz questions against the Mental Model level, not the exact
   syntax — a question that only checks whether someone remembers a flag
   name tests recall of trivia, not understanding of the fix.
